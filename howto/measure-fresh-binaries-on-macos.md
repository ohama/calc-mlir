# macOS에서 새로 만든 실행 파일의 시간 재기

컴파일러가 만든 실행 파일을 `time`으로 재면 첫 결과가 이상하게 느리다. **같은 파일의 두 번째 실행부터는 빠르다.** 파일을 복사해서 새 파일을 만들면 다시 느려진다.

```
$ /usr/bin/time -p ./deep     # 방금 링크한 파일
real 0.35  user 0.02  sys 0.00
$ /usr/bin/time -p ./deep     # 같은 파일 두 번째
real 0.04
$ cp deep deep2 && /usr/bin/time -p ./deep2
real 0.35                     # 새 파일이라 다시 느림
real 0.01                     # 두 번째
```

## The Insight

**늘어난 시간은 `real`에만 있고 `user`와 `sys`는 거의 0이다.** 프로그램이 일하는 시간이 아니라, 프로그램이 시작되기 전에 무언가를 기다리는 시간이다. 새 실행 파일에만 생기므로 macOS가 처음 보는 바이너리를 검사하는 비용으로 보인다(서명이나 정책 검사로 추정되며, 원인 자체는 확인하지 않았다).

- **어느 바이너리에서나 생긴다:** 아무 일도 하지 않는 `hello`도 첫 실행이 0.35~0.39초였다. Apple clang으로 만들어도, 스택 옵션이나 GC가 없어도 같았다.
- **병렬로 돌려도 줄지 않는다:** 새 `hello` 8개를 동시에 실행하면 2.57초(≈ 8 × 0.32초)가 걸렸다. 같은 8개를 다시 실행하면 0.03초였다. 검사가 하나씩 순서대로 처리된다.

## Why This Matters

- **벤치마크:** 첫 실행 하나로 재면 `fib 30`이 0.37초로 나옵니다. 실제로는 0.01초라서 인터프리터(0.94초)와 비교한 결론이 크게 달라집니다.
- **테스트 시간:** differential testing은 예제마다 새 실행 파일을 만들고 **한 번만** 실행합니다. 예제 약 220개 × 약 0.37초가 순서대로 쌓여, 테스트 1분 30초의 대부분이 이 비용이었습니다. 병렬로 컴파일해도 줄지 않았습니다.

## Recognition Pattern

- `time` 결과에서 `real`이 `user + sys`보다 훨씬 클 때
- 컴파일러, 링커, 코드 생성 도구가 만든 바이너리를 macOS에서 잴 때
- 같은 실행 파일의 첫 실행만 느릴 때

## The Approach

### Step 1: 같은 파일을 여러 번 실행해서 첫 번째를 버린다

```bash
for i in 1 2 3; do /usr/bin/time -p ./prog 2>&1 | grep real; done
```

### Step 2: `real`과 `user + sys`를 함께 본다

차이가 크면 계산 시간이 아니라 기다리는 시간이다. 프로그램 성능을 말할 때는 `user`를 기준으로 삼는다.

### Step 3: 테스트 시간을 줄일 때는 새 실행 파일 수를 줄인다

병렬화로는 줄지 않는다. 예제를 실행 파일 하나로 묶고, 그 안에서 예제마다 `fork`하게 바꾸면 첫 실행 비용을 한 번만 낸다(`batch-compiled-test-programs-into-one-executable.md`). 이 프로젝트에서는 1분 30초가 약 5초가 되었다.

## Example

```
fib 30 (커링한 add, 클로저 할당 100만 번 이상)
  첫 실행:       real 0.37  user 0.03
  두 번째부터:   real 0.01  user 0.01
  인터프리터:    real 0.94  user 0.90
```
