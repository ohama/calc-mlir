# 성능 비교: Python, 인터프리터, 컴파일러

같은 일을 하는 예제 다섯 개를 Python, Calc 인터프리터, Calc 컴파일러로 실행해 출력과 시간을 비교합니다. 프로그램과 측정 스크립트는 [benchmarks/](../benchmarks/)에 있습니다.

```bash
dotnet build src/Calc -c Release
python3 benchmarks/run.py        # 예제마다 5번씩 (python3 benchmarks/run.py 10 이면 10번)
```

스크립트는 세 결과의 출력이 다르면 멈춥니다.

## 예제

| 예제 | 하는 일 | 보려는 것 |
|---|---|---|
| [fib](../benchmarks/fib.calc) | `fib 32` (호출 약 700만 번) | 함수 호출, tail call이 아닌 재귀 |
| [queens](../benchmarks/queens.calc) | 10×10 N-Queens 해의 개수 | 리스트, backtracking, 안쪽 `let rec` |
| [sieve](../benchmarks/sieve.calc) | 200만까지의 소수 개수 (에라토스테네스의 체) | 배열, `while`, `for`, `ref` |
| [msort](../benchmarks/msort.calc) | 정수 20만 개의 merge sort | 리스트 할당, 튜플 패턴 매칭 |
| [bst](../benchmarks/bst.calc) | 이진 탐색 트리에 20만 개 넣고 20만 번 찾기 | algebraic data type, 새 노드 할당 |

- **같은 출력:** Calc의 `int`는 32비트에서 한 바퀴 돌고 Python의 `int`는 크기 제한이 없습니다. 그래서 중간값이 2³¹을 넘지 않게 만들었습니다. 난수는 작은 LCG(`(x * 75 + 74) % 65537`)로 만들고, 합은 나머지 연산으로 줄입니다.
- **Python 쪽:** 같은 알고리즘을 Python답게 썼습니다.
  - queens와 sieve는 `for`와 `while`을 씁니다.
  - bst는 노드를 불변 튜플로 새로 만듭니다(Calc와 같음). 찾기는 반복문입니다.
  - msort는 연결 리스트가 아니라 Python 리스트(배열)와 slicing을 씁니다. 그래서 msort는 자료 구조까지 같은 비교는 아닙니다.

## 결과

Apple M4 Max, CPython 3.15.0(JIT 없음), clang 22.1.7(`-O2`), Release 빌드. 실행 파일은 0.56.0의 컴파일러 변경(태그를 떼지 않는 덧셈과 뺄셈. 아래 "할당이 많은 프로그램" 절)을 넣은 뒤, 인터프리터는 `dotnet build`의 결과로 잰 값입니다. ReadyToRun으로 publish한 결과는 아래 따로 적었습니다. 시간은 초, 한 번 데운 뒤 5번 잰 중앙값이며 프로세스 시작을 포함한 wall time입니다.

## 관찰

### 호출, 반복, 배열은 컴파일러가 크게 빠르다

fib, queens, sieve에서 실행 파일은 Python보다 5~18배 빠릅니다. 알려진 함수는 direct call, 꼬리 위치의 호출은 tail call이 되고(`tailcc`), 정수는 tagged 값이라 상자에 넣지 않습니다. queens는 일이 작아서 시작 비용 차이(0.014초와 0.005초)가 배율에 크게 들어갑니다.

### 할당이 많은 프로그램은 GC가 비용이다

0.48.0까지 msort와 bst는 Python과 비슷했습니다(0.17초, 0.22초). 0.48.0 다음에 macOS의 `sample`로 실행 파일을 잰 결과와 고친 것을 이 절의 끝에 적었습니다. 그 전의 기록은 다음과 같습니다.

msort와 bst는 Python과 비슷합니다. msort는 0.44.0까지 Python보다 느렸습니다(0.29초). prelude의 `reverse`와 `append`가 원소마다 `fold`에 넘긴 클로저를 `calc_apply`로 불렀기 때문입니다. 직접 재귀로 바꾼 뒤 0.20초가 되었습니다. 이유 세 가지를 보았습니다.

- **GC (확인함):** Boehm GC의 처음 힙을 키우면 시간이 줄어듭니다. msort는 GC가 65번 돌고 힙이 약 34MB까지 커집니다.

  ```bash
  calc --compile=msort benchmarks/msort.calc
  GC_PRINT_STATS=1 ./msort                    # 수거 횟수와 힙 크기
  GC_INITIAL_HEAP_SIZE=1000000000 ./msort     # msort 약 0.27초 → 0.22초, bst 0.20초 → 0.14초
  ```

- **비교 연산 (추정):** Core IR에는 타입이 없어서 `<`, `<=`, `=`는 인자가 int인지 string인지 모릅니다. 그래서 C 런타임의 polymorphic `calc_compare`를 부릅니다. 생성한 MLIR에서 msort는 4곳, bst는 7곳입니다(`calc --emit-mlir`로 확인). 호출 비용을 따로 재지는 않았습니다.
- **자료 구조:** msort의 Python 쪽은 배열이라 원소마다 블록을 할당하지 않습니다.

0.48.0 다음에 잰 것입니다. 입력을 10배로 키우고 실행 중인 프로세스를 `sample <pid> 1`로 1초 동안 잤습니다.

| 프로그램 | 시간을 쓴 곳 |
|---|---|
| fib 41 | `calc_compare` 54%, `calc_add` 24%, 본체 22% |
| bst | Boehm GC 약 75% (`GC_mark_from`, `GC_reclaim_generic`, `GC_malloc_kind`), 본체 21%, `calc_compare` 3% |
| msort | Boehm GC 대부분. 할당마다 `GC_malloc` → dylib stub → `pthread_getspecific` |

| 변경 (실행 파일, 초 / 최대 메모리) | fib | queens | sieve | msort | bst |
|---|---|---|---|---|---|
| 0.48.0 | 0.014 | 0.012 | 0.022 | 0.171 / 38MB | 0.215 / 13MB |
| `+`, `<`, `>`, `<=`, `>=`, `=`의 int(`=`는 즉시값) 경로를 생성 코드에서 바로 | 0.010 | 0.008 | 0.018 | 0.164 | 0.208 |
| 8단어까지의 블록은 `GC_malloc_many`로 한꺼번에 받아 런타임이 나눠 줌 | | | | 0.150 | 0.199 |
| `GC_set_free_space_divisor(1)` (수거를 드물게) | 0.010 | 0.008 | 0.018 | 0.097 / 72MB | 0.130 / 20MB |

`GC_malloc_many` 행은 그것만 따로 잰 값이고, 마지막 행은 셋을 모두 넣은 값입니다. fib 41은 0.86초에서 0.42초가 되었습니다.

- **해 보았지만 넣지 않은 것:**
  - **LTO:** 런타임과 생성 코드를 함께 최적화하면 fib 41이 16% 빨라졌습니다. 그러나 homebrew LLVM의 `lld`는 512MB 스택 옵션(`-stack_size`)을 지원하지 않고, Apple `ld`는 LLVM 22의 bitcode를 읽지 못했습니다.
  - **Boehm의 incremental 모드:** msort가 1.5배, bst가 2배 느려졌습니다.
  - **처음 힙을 크게:** free space divisor와 효과가 비슷하지만, 작은 프로그램도 메모리를 그만큼 씁니다.

0.49.0 다음에 다시 잰 것입니다.

| 프로그램 (0.49.0) | 시간을 쓴 곳 |
|---|---|
| bst | 대부분 GC(`GC_mark_from`, `GC_reclaim_generic`). 트리 노드 하나가 data 블록과 튜플 블록 두 개 |
| msort | 블록 할당(`calc_alloc`, `calc_cons`). 새 메모리를 처음 쓰는 비용 |
| sieve | 배열 원소 읽기와 쓰기가 런타임 함수 호출 |
| 시작 | 빈 C 프로그램 2.47ms, libgc 동적 링크와 `GC_INIT` 3.19ms, 실행 파일 3.25ms. libgc를 정적으로 링크해도 0.3ms |

| 변경 (실행 파일, 초) | fib | queens | sieve | msort | bst |
|---|---|---|---|---|---|
| 0.49.0 | 0.010 | 0.009 | 0.018 | 0.097 | 0.131 |
| 배열 읽기, 쓰기를 생성 코드에서 (범위 검사 후 load/store) | 0.010 | 0.008 | 0.017 | 0.097 | 0.131 |
| 생성자의 튜플 인자를 블록에 펴서 넣음 (`[헤더, 이름, 원소...]`) | 0.009 | 0.008 | 0.017 | 0.097 | 0.064 |

- **배열:** sieve를 3천만으로 키우면 0.32초에서 0.27초가 되었습니다.
- **생성자 값:** 트리 노드 하나가 블록 둘에서 하나가 되어 bst가 반이 되었습니다. 단어 수가 2면 튜플이 아닌 인자 하나, 3 이상이면 편 원소들이라서 컴파일러가 생성자의 인자 수를 몰라도 됩니다.
- **msort:** 연결 리스트의 칸을 새로 만드는 비용이 남았습니다.

0.50.0 다음에 다시 잰 것입니다.

| 변경 (실행 파일, 초) | fib | queens | sieve | msort | bst |
|---|---|---|---|---|---|
| 0.50.0 | 0.010 | 0.008 | 0.017 | 0.097 | 0.064 |
| `append (reverse xs) ys`를 런타임의 `calc_rev_append` 하나로 (리스트 칸 2n개 → n개) | 0.010 | 0.008 | 0.017 | 0.080 | 0.064 |
| `match (a, b) with`에서 튜플 블록을 만들지 않고 원소마다 맞춤 | 0.009 | 0.007 | 0.017 | 0.064 | 0.064 |

- **해 보았지만 효과가 없던 것:**
  - **`GC_MARKERS=2, 4, 8`:** 변화가 없었습니다. homebrew의 libgc가 병렬 표시를 쓰지 않는 것으로 보입니다.
  - **clang `-O3`, `-mcpu=native`:** 측정 오차 수준이었습니다.
  - **`GC_set_all_interior_pointers(0)`:** Boehm은 객체 끝을 가리키는 포인터를 위해 1바이트를 더 붙여서, 16바이트 요청이 32바이트가 됩니다. 이 설정을 끄면 크기는 맞습니다. 하지만 이 예제의 블록(cons 24B, `Node` 40B)은 어차피 32B, 48B로 올라가 효과가 없었습니다.
- **인터프리터도 같은 관용구를:** 0.52.0에서 인터프리터도 `append (reverse xs) ys`를 한 번에 처리합니다(`Eval.revAppend`). 인터프리터의 msort가 0.665초에서 0.611초가 되었습니다.
- **헤더 없는 cons 칸 (0.53.0):** 먼저 같은 할당기에서 칸 크기만 바꾼 C merge sort로 효과를 가늠했습니다. 24바이트 칸은 0.90초/575MB, 16바이트 칸은 interior pointer를 켜면 0.92초(여전히 32바이트), 끄면 0.64초/281MB였습니다. 그래서 cons를 헤더 없는 `[head, tail]` 블록과 값의 태그 `2`로 바꾸고, interior pointer를 끈 뒤 `GC_register_displacement(2)`로 주소 + 2를 알렸습니다. msort가 0.064초에서 0.049초, 최대 메모리가 72MB에서 38MB가 되었습니다.
- **해 보았지만 넣지 않은 것 (0.53.0 조사):**
  - **할당을 생성 코드에서 바로 (free list에서 꺼내기):** 변화가 없었습니다. 할당 함수를 부르는 비용은 병목이 아닙니다.
  - **타입으로 int를 확정해 태그 검사 없애기 (상한):** fib 41이 0.43초에서 0.33초(C는 0.28초)였지만, bst, msort, sieve의 큰 입력은 그대로였습니다. 0.54.0에 넣었습니다(아래).

### 인터프리터는 CPython과 비슷하거나 5배까지 느리다

함수 호출 하나의 비용은 CPython과 비슷합니다. 재귀 호출 `loop (i - 1)` 한 번이 둘 다 약 33ns입니다. 차이는 호출 바깥에서 납니다. 아래 수치는 같은 프로세스에서 `Eval.eval`을 여러 번 부르며 `Stopwatch`, `GC.GetTotalAllocatedBytes`, `GC.GetTotalPauseDuration`으로 잰 값입니다(빠른 경로를 넣기 전).

| 예제 | 시작 | JIT 데우기 | 평가 (데운 뒤) | 그중 GC pause | 할당량 |
|---|---|---|---|---|---|
| fib | 약 0.13 | 0.06 | 0.19 | 0.005 | 0.9 GB |
| queens | 약 0.12 | 0.09 | 0.13 | 0.003 | 0.5 GB |
| sieve | 약 0.12 | 0.16 | 1.34 | 0.04 | 3.4 GB |
| msort | 약 0.13 | 0.10 | 2.63 | 0.63 | 7.2 GB |
| bst | 약 0.13 | 0.08 | 1.83 | 0.53 | 3.4 GB |

- **시작 비용과 JIT (fib, queens):**
  - 시작 비용은 .NET 시작과 명령줄 처리 0.07초(`calc --version`), 파싱과 prelude 0.03초, 타입 검사 0.015~0.025초입니다. CPython은 0.014초입니다.
  - .NET은 처음에 최적화하지 않은 코드로 시작하므로 첫 평가가 0.06~0.16초 더 걸립니다.
  - 데운 뒤 fib는 호출 한 번에 27ns이고 CPython은 17ns입니다.
- **Python에서 명령 하나인 것이 Calc에서는 함수 호출 (sieve):**
  - CPython 3.11부터 bytecode가 실행 중에 정수, 리스트용으로 바뀝니다(`BINARY_OP_ADD_INT`, `STORE_SUBSCR_LIST_INT`). 그래서 `while` 한 바퀴가 8ns, `c += 1`이 3ns 정도입니다.
  - Calc의 `while`은 재귀 함수 호출이고, 가변 변수는 `ref`이며, `!`, `:=`, `a.[i]`, `a.[i] <- v`는 내장 함수 호출입니다.
  - 내장 함수 호출은 인자 하나마다 `VBuiltin`을 새로 만들어 인자 리스트를 `@`로 복사합니다. 인자가 다 모이면 인자 수를 `Map`에서 문자열로 찾습니다. 마지막으로 `callBuiltin`의 `match`가 문자열을 차례로 비교합니다(`.[]<-`는 28번째).
  - 그래서 `c := !c + 1; i := !i - 1` 반복 한 바퀴가 205ns, 504바이트였습니다. CPython은 14ns입니다.
- **모든 값이 heap 객체 (msort, bst):**
  - 빈 반복 한 번에 112바이트를 할당합니다. 내역은 `Frame`과 칸 배열 64바이트, 새 `VInt` 24바이트, 비교 결과 `VBool` 24바이트입니다.
  - 리스트는 F# 리스트를 `VList`로 한 번 더 감쌉니다. 그래서 `x :: rest` 패턴이 맞을 때마다 `VList rest`를 만듭니다.
  - 오래 사는 20만 개짜리 리스트 때문에 gen1, gen2 수거도 일어나고, GC pause가 평가 시간의 24~29%입니다.
  - CPython은 reference count로 바로 해제해 메모리를 다시 쓰고, 작은 정수는 캐시합니다.
- **해석하는 단계 수 (msort):**
  - Python 쪽의 slicing과 `extend`는 C 안에서 돕니다.
  - Calc 쪽은 `split`, `reverse`, `append`가 모두 해석하는 단계입니다. 0.44.0까지 prelude의 `append`는 reverse한 뒤 fold해서, `merge`가 끝날 때마다 남은 리스트를 세 번 훑고 원소마다 클로저를 불렀습니다.
  - GC pause를 빼도 CPython의 10배입니다.
- **.NET tail call:**
  - 반복을 F#의 tail call(`<Tailcalls>true</Tailcalls>`)에 맡기는 비용도 있습니다. 끄고 빌드하면 빈 반복이 33ns에서 17ns가 됩니다.
